The [canonical timeline business rules](timeline.md#canonical-timeline-business-rules) define the intended contract. This document records implementation progress, historical gap evidence and follow-up boundaries; closed ownership gaps do not certify complete compliance with the remaining business rules. The foundation is **PO works continuously. HoD controls publication.**

### Existing protections and stale-review boundary

Lifecycle requests already support same-stage supersession in `StageRequestService.CreateBatchAsync`; `StageDecisionService.DecideAsync` decides an exact request and conditionally claims a still-pending request for approval or rejection. The projected lifecycle also checks incompatible untouched pending proposals. Preserve these protections; a blanket claim that lifecycle decisions have no stale-request protection would be incorrect.

Plan review is a separate gap: `Pages/Projects/Timeline/Review.cshtml.cs`, `OnPostAsync`, calls latest-plan approval/rejection methods by project ID. `PlanApprovalService` also has an exact-version approval API, but that does not make the page's latest-version decision safe for the target revision contract. Phase C must bind both approval and rejection to the exact revision reviewed and reject an older decision after a material replacement. Removing the pending-plan lock without that protection would be unsafe. Withdrawal, cross-category revision identity and atomic coherent publication are not supplied by the existing separate paths.

## Implementation phases

The completed foundations are #2662 (lifecycle/actual-date integrity and published ARPP IPA authority), #2664 (Duration safety and generation semantics), #2665 (server-side planner action/authority matrix), and #2666 (canonical execution dependencies, published PNC applicability and direct-publication concurrency). Phase A is complete. This change completes B1; B2 is next. G01-G05 and the remaining work in G09-G14 are open; these foundations must not be mistaken for the later cross-category revision architecture. Each high-risk follow-up needs focused regression evidence, deployment impact and a reversible rollout. Preserve offline LAN operation, routes and operator interfaces, live-data compatibility and migration lineage. Assume overlapping deployed processes unless an explicit outage procedure guarantees otherwise. Do not introduce a migration, startup failure or enforcement gate merely to match the target: establish the actual prerequisite and a safe transition first.

## B1 persistence and deployment boundary

`PlanVersion` and its `StagePlans` are the complete actor-owned proposal state. `PlanVersion.SkipHolidays` is the missing policy field; `StagePlan.SortOrder` is required because supported legacy/extension stages cannot always derive their order from workflow metadata. Known stages continue to use canonical workflow order. Zero `StagePlan.DurationDays` means cleared input; published nullable duration rows use null, retaining compatibility rows.

Generation reads the selected proposal's scheduling policy and durations, plus current workflow metadata and the authoritative holiday calendar. It does not read shared settings/durations as mutable proposal inputs. Reads prefer the current actor's Draft, then their applicable Pending revision, then published settings/durations/stage dates and project applicability. Another user's proposal is never an editor baseline. Creating a draft clones only published state and does not create global settings/duration rows. The PO pending-plan lock remains until C supplies exact-revision decisions and supersession.

Approval publishes the reviewed revision's settings, durations/order, official dates and `Project.PncApplicable` within the existing relational transaction, including the snapshot and approval metadata. HoD/Admin explicit SaveChanges remains authoritative, preserving direct publication concurrency and Exact-derived compatibility durations. Private operations only update the actor's proposal; any direct-save draft synchronization is scoped to the current actor. The existing realignment proposal creator retains its approved-source stage date cloning/shifting, but initializes newly publishable policy, durations/order and PNC from one coherent read of the current published baseline. It cannot reinstate an older approved revision's inputs after a direct save. Missing published settings use a null anchor, weekend/holiday skipping and NextWorkingDay defaults; missing durations are cleared, with deterministic published-stage/metadata ordering fallback. Other actors' Draft/Pending inputs are never its baseline. B2 validation, forecasting and execution workflow redesign are excluded.

The additive migration `20261217000001_AddProposalOwnedPlanningInputs` backfills the new holiday policy from matching project schedule settings, defaulting to true when absent. Historical revisions created before this field existed did not persist their holiday-policy value independently, so exact historical reconstruction is impossible where project settings changed afterward. Existing anchor/weekend/transition/PNC, durations and dates are preserved. Extension sort backfill uses, in order, matching published duration sort order, official stage sort order, workflow metadata, then a deterministic StagePlan ID fallback. Subsequent known-stage generation remains canonical; extension order is revision-owned.

Apply the reviewed additive migration before deploying the matching application, using the coordinated update/rollback procedure in [the offline deployment SOP](deployment/offline-ws2022.md#d-offline-update-and-rollback-sop). Older processes can still write global planning inputs, so coordinate or pause planner writes during the transition; additive columns alone do not make mixed-version planner writes isolated. Resume writes only with the matching application version. Rollback requires a compatible application/database backup or reviewed down-migration plan under that SOP; do not edit migration history. This change has not inspected production configuration or production data.
