# Timeline proposal implementation roadmap

The [canonical timeline business rules](timeline.md#canonical-timeline-business-rules) define the intended contract. This document records current implementation deviations and proposed follow-up boundaries; it does not implement them or certify that current code already complies. The foundation is **PO works continuously. HoD controls publication.**

### Existing protections and stale-review boundary

Lifecycle requests already support same-stage supersession in `StageRequestService.CreateBatchAsync`; `StageDecisionService.DecideAsync` decides an exact request and conditionally claims a still-pending request for approval or rejection. The projected lifecycle also checks incompatible untouched pending proposals. Preserve these protections; a blanket claim that lifecycle decisions have no stale-request protection would be incorrect.

Plan review is a separate gap: `Pages/Projects/Timeline/Review.cshtml.cs`, `OnPostAsync`, calls latest-plan approval/rejection methods by project ID. `PlanApprovalService` also has an exact-version approval API, but that does not make the page's latest-version decision safe for the target revision contract. Phase C must bind both approval and rejection to the exact revision reviewed and reject an older decision after a material replacement. Removing the pending-plan lock without that protection would be unsafe. Withdrawal, cross-category revision identity and atomic coherent publication are not supplied by the existing separate paths.

## Proposed implementation phases

These are proposed small PR boundaries, not implementation instructions for this documentation change. Each high-risk follow-up needs focused regression evidence, deployment impact and a reversible rollout. Preserve offline LAN operation, routes and operator interfaces, live-data compatibility and migration lineage. Assume overlapping deployed processes unless an explicit outage procedure guarantees otherwise. Do not introduce a migration, startup failure or enforcement gate merely to match the target: establish the actual prerequisite and a safe transition first.

| Phase | Scope | Required validation before publication |
| --- | --- | --- |
| A — Defect containment | Correct duration submitter/action delivery and role-safe autosave; prevent unintended direct publication and misleading save feedback. | Exercise real browser submit/autosave behavior, PO versus HoD/Admin, unsaved inputs, failure/redirect feedback, explicit save and no unintended authoritative writes. Preserve existing valid behavior. |
| B — Shared planned/PDC validity | One graph/transition/calendar rule set for PO proposals and HoD/Admin direct saves; consistent Exact/Duration policy, proposal input/discard semantics. | SameDay/NextWorkingDay, holidays/weekends, branching/convergence/skipped ancestry, local ordering, optional partial/future plans and missing current InProgress PDC warning; equivalent PO/direct validity and no mutation on rejection. |
| C — Non-blocking revisions | Immutable material revisions, withdrawal/resubmission/replacement, supersession, durable history and stale decisions without PO locks. | HoD opens N, PO creates N+1: both approve and reject N fail without mutation; only latest actionable submitted revision succeeds. Cover repeated revisions, withdrawal, concurrent edits/decisions, pending-stage protections, exact plan review identity and discarded inputs. |
| D — Approved actual correction/backfill | Route PO actual corrections and completion backfill through HoD proposals; shared final-state graph validity; preserve ARPP authority. | No official mutation before approval; coordinated predecessor/successor corrections and affected untouched descendants; IST/factual/status rules; optional Completed Actual start, explicit clearing, reopen, same-day chronology, completion-without-date and published/draft ARPP cases. |
| E — Timeline Change Set | Coordinate Plan, Actual fact correction and Lifecycle in one revision while retaining semantic categories and coherent publication/audit. | Multi-stage/category final-state validation; atomic publication and audit, rejection/withdrawal/supersession, concurrent source changes, retry and overlapping-process safety. No partial authoritative application of a coherent revision. |
| F — PO experience | Update; Planned start/PDC and Actual start/Actual completion; official/proposed/status distinction; stage quick update, bulk Update project plan and concise submission diff. | One-field updates without forced bulk editor, continued editing while pending, accessible approval/status messaging, graph/client/server parity and no storage-model choices required of the PO. |
| G — HoD review | Exact revision, submitter/time, grouped current/proposed diff, downstream impact and stale-review reload guidance using the same proposal representation as the PO. | Reviewed/submitted/persisted values agree; stale approve/reject UX, category/impact visibility and durable reconstruction of before/proposed/after values and every decision. |

Keep reopening, inclusive calendar-day actual duration, same-day actual chronology and the canonical status/date matrix intact throughout. Published ARPP must still persist IPA Completed with IssueDate, clear backfill/auto-completion flags, supersede pending manual IPA completion, preserve genuine Actual start and leave unknown start null; draft ARPP must not complete or lock IPA, and defensive effective-state projection remains a safety net.

No phase is implemented by this PR. Runtime behavior, migrations and production data remain unchanged.
