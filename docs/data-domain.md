# Data and Domain

This module covers the persistence layer and core domain types.

## Data layer

### `Data/ApplicationDbContext.cs`
Derives from `IdentityDbContext<ApplicationUser>` and exposes tables for `Projects`, `TodoItems`, `Celebrations`, `AuthEvents`, `DailyLoginStats`, `AuditLogs` and now `Events` for the calendar. Indexes on `TodoItem` enforce fast lookups by owner and due date, while `Event` rows are filtered by `IsDeleted` and indexed on `StartUtc` and `EndUtc` for range queries. Identity tables (users, roles, claims, etc.) are provided by the base class.

### `Data/DesignTimeDbContextFactory.cs`
Provides a design-time factory so Entity Framework tooling can create the context when running migrations. It reads configuration from `appsettings.json`, `appsettings.Development.json`, or environment variables.

### `Data/IdentitySeeder.cs`
Seeds the initial application roles. If the configured bootstrap administrator does not yet exist, startup requires a one-time secret through `PRISM_BOOTSTRAP_ADMIN_PASSWORD` or `Security:BootstrapAdminPassword`. The account is created with `MustChangePassword` enabled; remove the bootstrap secret after successful creation. Development test users are seeded only when explicit `DevelopmentSeedUsers:*:Password` values are configured.

## Domain model

### `Models/ApplicationUser.cs`
Extends `IdentityUser` with a `MustChangePassword` flag. New accounts are created with the flag set to `true`, forcing a password change on first login via `EnforcePasswordChangeFilter`.

### `Models/Project.cs`
Holds the master record for a project. Beyond its name/description it stores the case file reference, creator, category, active plan version and assignment metadata for the Head of Department and Lead Project Officer. `PlanApprovedAt/ByUserId` capture the latest plan approval event and the navigation properties surface related user records for UI display. `ProjectStages` now owns the execution stages collection and the obsolete `Stages` property simply proxies to it for backward compatibility.

### `Models/ProjectCategory.cs`
Allows projects to be organised in a hierarchy. Each category exposes a `ParentId` so breadcrumb trails can be built and circular references are guarded against in the overview loader.

### `Models/Execution/ProjectStage.cs`
Represents each procurement or delivery milestone for a project. Rows track planned, forecast and actual dates, completion status, auto-completion metadata and whether the stage still needs backfilling. The `StageCodes` helper enumerates canonical codes (FS, IPA, SOW, …, PAYMENT) and exposes human readable display names.

### Actual stage facts, lifecycle requests and stage history (`Models/Execution/ProjectStage.cs`, `Models/Stages/StageChangeRequest.cs`, `Models/Stages/StageChangeLog.cs`)
`ProjectStage.Status`, `ActualStart`, `CompletedOn`, `RequiresBackfill` and the auto-completion markers are the official Actual facts. They are written by Actual correction and completion backfill (`StageActualsUpdateService`, `StageBackfillService`, both through `ActualFactPublisher`), by lifecycle writers (`StageDirectApplyService`; `StageDecisionService` through `StageProgressService`; `HistoricalStageRecordService` for closed legacy projects), by `ArppIpaStageSynchronizer` for a published ARPP IPA, and at project creation. Phase D-1 hardened these writers; it did not change who may use them. An assigned Project Officer still publishes Actual corrections and backfill directly until D-2/D-3, which are approved (PO-only users will submit proposals decided by a HoD or Admin) but not implemented ([Phase D plan](phase-d-implementation-plan.md#implementation-status)).

* **Validation.** Actual correction and backfill are refused unless the complete final stage state passes the shared `IActualTimelineValidationService` (D-1a/D-1b). Lifecycle writers keep their own rules and are not blocked by chronology: since D-1d they log `Stages.ActualChronologyWarning` after commit for a violation they introduce (`Stages.ActualChronologyWarningUnconfirmed` when a caller owns the transaction; `Stages.ActualChronologyWarningFailed` if the observation fails). ARPP is exempt (rule 17).
* **Locking.** The *project gate* is `PlanRevisionConsistency.LockProjectAsync`, a PostgreSQL transaction-scoped advisory lock per project (a no-op row update on SQLite). Actual correction, backfill, lifecycle decisions, lifecycle request submission, HoD direct apply and plan publication take it first. Actual correction, backfill, decisions and submission then lock all the project's stage rows (`SELECT … ORDER BY "Id" FOR UPDATE`) before reading stage facts, and only then touch request rows; direct apply also locks stage rows before ARPP authority checks (PR #2680, merge `207acd82`); plan publication relies on the gate alone. Actual correction and backfill also re-read the project row `FOR SHARE` to re-establish authority. ARPP synchronization is different: it does not take the gate, but locks the IPA rows it will update (`FOR UPDATE`, `Id` order) before reading them, then updates request rows. `HistoricalStageRecordService` takes no gate.
* **Stale forms.** The Actual editor and the backfill form post a per-stage `ActualStageToken` (SHA-256 over `StageCode`, `Status`, `ActualStart`, `CompletedOn`, `RequiresBackfill`). A post that would change a stage whose token no longer matches is refused without writes; a stage the post does not change needs no matching token. Posts without the baseline marker are still accepted and logged during Phase D-1.
* **Backfill flag.** A date correction keeps a raised `RequiresBackfill` on a stage that already had a completion date (missing facts); supplying a missing completion date clears it.
* **`StageChangeLog`** is the mandatory stage history. Each writer saves it in the same transaction as the stage change it records, so a failure rolls back both. Secondary `AuditLogs` entries and notifications for Actual correction, backfill, lifecycle decisions and ARPP synchronization run after commit (`RelationalTransactionScope.RegisterAfterCommit`) and cannot undo the change. `HistoricalStageRecordService` still writes its audit entry inside its transaction.
* **`StageChangeRequest`** holds lifecycle requests. The filtered unique index `ux_stagechangerequests_pending` allows one `Pending` request per project stage, and `CK_StageChangeRequests_DecisionStatus` limits `DecisionStatus` to `Pending`, `Approved`, `Rejected` and `Superseded`. Approval, rejection, submission supersession and ARPP supersession are each a compare-and-set `WHERE "DecisionStatus" = 'Pending'`, so between those writers a request reaches one terminal state, written by one writer, with one matching history row. HoD direct apply supersedes only a still-pending request by conditional update after the project gate and stage-row locks (PR #2680, merge `207acd82`). A separate pre-existing missing-IPA-row insertion conflict remains an accepted, recoverable rollback-and-retry limitation (see the [D-1 verification findings](phase-d-implementation-plan.md#d-1-verification-findings)).
* **ARPP.** Synchronization completes a published IPA on the ARPP issue date, keeps a recorded `ActualStart`, clears the backfill and auto-completion flags, and supersedes still-pending IPA requests (with a `Superseded` history row). The completion itself and any data-quality conflict are recorded as post-commit `AuditLogs` entries (`Arpp.IpaStageSynchronized`, `Arpp.IpaStageDataQualityIssue`), not as `StageChangeLog` rows.

### `Models/ProjectFacts.cs`
Defines fact tables that capture procurement milestones. IPA, AON, benchmark, L1 and PNC costs, along with the supply-order date and SOW sponsoring units, derive from a shared `ProjectFactBase` that records who captured the fact and when. Each fact table carries a concurrency token so editors get reliable conflict detection when procurement numbers evolve.

### `Models/TodoItem.cs`
Represents a personal task owned by a user. Each item records a title, due date (stored in UTC), priority, pin state, order index and timestamps for creation, updates, completion and soft deletion. PostgreSQL's `xmin` concurrency token is used to detect conflicting edits. Items marked completed are soft-deleted by setting `DeletedUtc`; a background worker purges entries older than the configured retention period.

### `Models/Celebration.cs`
Stores birthdays and anniversaries with minimal fields for annual recurrence. Each row tracks the event type, name(s), day and month, optional year, creator metadata and soft-delete timestamp. Indexes on `(EventType, Month, Day)` enable fast upcoming lookups and a filtered index on `DeletedUtc` hides removed entries. Leap day events are rendered on 28 February in non-leap years.

### `Models/AuthEvent.cs`
Records successful authentication events. Each row stores the user ID, timestamp (UTC), IP address and user agent for audit and analytics. Indexed by event name and time for efficient querying.

### `Models/DailyLoginStat.cs`
Holds pre-aggregated daily login counts generated by `LoginAggregationWorker`. Aggregation reduces load on the primary `AuthEvents` table for long-range reporting.

### `Models/Event.cs`
Represents a calendar event visible to all signed-in users. Each row stores a title, optional Markdown description, category, location, UTC start/end times (exclusive end), an `IsAllDay` flag and creator/updater metadata. Soft deletion hides events without removing them from the database. Categories are restricted to **Visit**, **Insp**, **Conference** and **Other**; legacy values like "Training" or "TownHall" are mapped by `CategoryParser` and unrecognised strings fall back to `Other`.

### `Models/ProjectVideo.cs`
Stores uploaded project walkthrough videos. Metadata includes the storage key, original filename, MIME type, optional duration, title, description, ordinal ordering, featured flag, and poster frame references. Videos live beneath the upload root resolved by `IUploadRootProvider`, and posters share the same deterministic folder hierarchy. (see Models/ProjectVideo.cs lines 1-38) (see Services/Projects/ProjectVideoService.cs lines 82-420)

### `Models/AuditLog.cs`
Captures structured audit entries with timestamps, action names, user metadata, IP addresses and optional payloads. Sensitive fields are scrubbed by `AuditService` before persistence.

### Transfer of Technology tracker (`Models/ProjectTot*.cs`)
`ProjectTot` holds the authoritative ToT status for a project, capturing milestones (start/completion dates, MET progression, first-production manufacture) and the last approver metadata. `ProjectTotRequest` stores pending updates with proposed values, submitter/decider metadata, and a concurrency token so approvals reject stale decisions. Both entities underpin the ToT tracker in the Project Office Reports area and are surfaced through dedicated read services. (see Models/ProjectTot.cs lines 1-37) (see Models/ProjectTotRequest.cs lines 1-38)

### Timeline planning and scheduling (`Models/Plans`, `Models/Scheduling`)
Timeline proposals are stored as `PlanVersion` rows with `StagePlan` children. A project may have independent actor-owned Drafts, at most one pending submission under the existing lock, and approved-version history. `OwnerUserId` scopes private edits; another actor's Draft or Pending revision is never the editor baseline.

* **Draft** rows are private working state for the acting authorised PO/HoD/Admin. `PlanVersion` owns `AnchorDate`, `SkipWeekends`, `SkipHolidays`, `TransitionRule` and proposal `PncApplicable`. `StagePlan` owns `StageCode`, non-null `DurationDays` (zero means cleared), calculated/exact `PlannedStart`/`PlannedDue`, and `SortOrder` for deterministic legacy/extension order. Known-stage ordering remains canonical workflow metadata. Private Autosave/SaveDraft/Calculate and PO Submit do not change global settings/durations, official dates or live applicability. New version 1 drafts copy the accepted baseline; deletion discards all private inputs without restoration of shared state. Legacy version 0 drafts upgrade at their actor's first explicit Exact/Duration edit before submitted edits apply, using the field-level cutover rules below.
* When a PO selects *Save & request approval*, `PlanApprovalService.SubmitAsync` validates the stage data and transitions the record to **PendingApproval**, stamping `SubmittedByUserId`/`SubmittedOn`. The draft becomes read-only until the Head of Department (HoD) acts.
* HoDs review diffs via `PlanCompareService.GetDraftVsCurrentAsync`, with UI highlights showing the left/right comparison. Approving a complete version 1 revision atomically publishes reviewed revision settings into `ProjectScheduleSettings`, durations/order into `ProjectPlanDuration`, stage dates into `ProjectStages` and applicability into `Project.PncApplicable`, records an immutable snapshot (`ProjectPlanSnapshot` + rows), updates `Project.PlanApprovedAt/ByUserId` and marks the version **Approved**. All publication writes, including the project version 1 marker, reuse the existing relational transaction; zero proposal durations become nullable cleared compatibility values without deleting rows. Legacy version 0 Pending approval publishes only its dates and historical PNC flag, preserving compatibility rows and the project marker.
* Rejection stamps the reviewer/time and optional `RejectionNote`. Legacy pre-C2 rejected proposals may return to their Draft identity for mode-aware editing; C2 submitted revisions are immutable on rejection, with corrections proceeding in a separate actor-owned Draft. Do not apply the legacy same-ID resubmission rule to C2 submissions.
* The new `RejectedByUserId` column is a nullable foreign key to `AspNetUsers`; the previous `Reason` column has been renamed to `RejectionNote`.
* Backfill guards are enforced both in the UI and server (`PlanApprovalService.ApproveLatestDraftAsync`) to prevent approval while earlier stages require completion.

`IPlannedTimelineValidationService` is the canonical Planned start/PDC validation boundary for PO submission, approval-time revalidation and authorised direct Exact/Duration publication. Its source-neutral candidate contains the complete projected stage state, proposal or accepted calendar/transition policy, anchor and explicit candidate PNC applicability. It resolves configured dependencies and fallback topology through `IProjectStageWorkflowPolicy`, with candidate PNC controlling the PNC branch independently of live `Project.PncApplicable`; sort order is deterministic presentation/generation metadata and does not create dependencies. Intrinsic ranges and every evaluable direct predecessor are checked with `WorkingCalendar` and `IOfficeCalendarService`. Missing dates remain valid when a rule cannot be evaluated, skipped official stages are excluded, and pre-anchor stages are not newly constrained. This planned-domain service is distinct from execution/lifecycle `StageValidationService`.

Submission validates the full proposal before Draft becomes PendingApproval. A rejected Submit retains the user's private edits as Draft work, but leaves submission metadata unchanged and sends no notification or publication. Approval re-reads current office-calendar facts and revalidates immediately before publication. Current proposals supply their own policy and must retain configured stages at or after the anchor, although their dates may remain partial. Legacy Pending proposals supply historical dates and PNC but use the accepted published policy or conservative B1 defaults; historical sparse proposals remain exempt from the new configured-stage completeness check while every represented date and dependency is still validated. Direct Exact overlays submitted rows, including null clears, on the retained official projection before any mutation. Direct Duration generates provisionally inside the relational publication transaction and validates the complete resulting official projection, including manual and extension stages, before draft synchronization, audit and commit. Invalid approval or direct publication leaves authoritative, snapshot, approval and publication-audit state unchanged. Private Autosave, SaveDraft and Calculate remain non-authoritative and are not whole-proposal enforcement boundaries. B2 requires no schema change.

`PlanRealignmentService` preserves its existing approved-source stage selection and date-shift algorithm. Its complete version 1, owner-null automatic Pending revision takes publishable anchor/calendar/transition settings, durations/order and live project PNC from a coherent current published-baseline read, preserving later direct-save decisions instead of reinstating historical approved inputs. Missing or untrusted settings use a null anchor, weekend/holiday skipping and NextWorkingDay; missing durations are zero and known order uses canonical template/workflow metadata, with extension order falling back to accepted duration order, official stage order and deterministic source StagePlan ID. Other actors' private Draft/Pending revisions are not its baseline.

`PlanEditorStateVm` gathers the metadata (status, submission/rejection timestamps, lock state) consumed by Razor components so that locking, banners and validation messaging stay consistent across edit and review experiences.

The existing B1 migration `20261217000001_AddProposalOwnedPlanningInputs` adds `PlanVersion.SkipHolidays` and `StagePlan.SortOrder`. The additive correction migration `20261217000002_VersionPlanningInputAuthority` adds `PlanVersion.PlanningInputVersion` and `Project.PublishedPlanningInputVersion`, preserving the earlier migration unchanged. Valid input versions are 0 (legacy/incomplete or untrusted) and 1 (complete B1 ownership or trusted B1 publication). Database defaults are 0: existing projects and every historical Draft, Pending and Approved revision remain conservatively legacy. New application-created proposals use version 1 immediately. The correction migration does not overwrite settings, durations or historical proposal fields. Earlier holiday-policy and extension-order backfills preserve compatibility data; column presence and generic historical defaults do not prove ownership. Historical shared private/published ownership and planning mode cannot be reconstructed with certainty; fields copied into a private revision by pre-B1 Duration generation are retained at its explicit Duration upgrade.

Pre-B1 private Duration SaveDraft/Calculate operations wrote shared settings/durations, which could survive discard. No heuristic based on draft presence, active/latest versions, timestamps, stage rows or PNC state promotes these globals. Project version 0 rows remain physically stored but are excluded from accepted planning inputs. The accepted legacy baseline uses authoritative official `ProjectStage.PlannedStart`/`PlannedDue` and `Project.PncApplicable`, a null anchor, weekend/holiday skipping, NextWorkingDay and cleared durations. This conservative policy may require deliberate re-entry of a legitimate pre-B1 direct policy; it preserves stored evidence without guessing or exposing another actor's private work.

Legacy Draft upgrade is mode-aware. Generic `CreateOrGetDraftAsync` retrieves the actor's revision without promoting or replacing its mode-specific fields. The actor's first explicit post-B1 Exact or Duration edit selects the upgrade; historical policy defaults, dates or other database heuristics never select a historical mode.

- **Exact:** snapshot accepted current baseline anchor, weekend/holiday and transition policy into the proposal; preserve its existing exact `StagePlan.PlannedStart`/`PlannedDue`; normalize PNC; recalculate every retained exact row's `DurationDays` under the accepted proposal calendar; mark `PlanningInputVersion = 1`; then apply submitted Exact edits. Generic pre-B1 Exact `AnchorDate`, `SkipWeekends` and `TransitionRule` do not gain policy authority.
- **Duration:** preserve the actor's own legacy `PlanVersion.AnchorDate`, `SkipWeekends` and `TransitionRule`, plus existing `StagePlan.DurationDays`, `PlannedStart`/`PlannedDue` and migration-backfilled extension `SortOrder`. Known stages retain canonical workflow order. Initialize `SkipHolidays`, which pre-B1 revisions did not own, from the accepted baseline (true when that baseline is untrusted), ignoring the compatibility migration's ambiguous copied holiday flag. Normalize PNC, mark version 1, apply submitted Duration inputs and generate dates from the resulting proposal. Omitted private durations survive. No shared `ProjectScheduleSettings` or `ProjectPlanDurations` row recovers private draft values.

Live false `Project.PncApplicable` overrides a legacy proposal's stale PNC flag, positive duration and dates: set proposal applicability false, duration zero and dates null. If live PNC is true, Duration upgrade retains the private proposal PNC input unless explicitly changed by the submitted form. Explicit submitted PNC re-enable remains available.

Before the first edit, owner reads may present the actor's legacy exact dates and private `StagePlan.DurationDays` without promoting the revision or writing anything. Live false PNC is presented cleared. This presentation does not trust old calendar-policy fields as current/published policy. Another actor never sees that private anchor, duration or extension and initializes new drafts only from the accepted published baseline. SaveDraft/Calculate and later discard leave published policy/durations, official dates, live PNC and authority markers unchanged; discard removes only that actor's proposal.

A legacy PendingApproval remains reviewable with pre-B1 authority: approval publishes StagePlan dates and its historical proposal PNC flag, without publishing generic policy/duration fields or promoting the project marker. Rejection returns it to Draft for the same explicit mode-aware first-edit upgrade.

Complete proposal approval or explicit authorised HoD/Admin SaveChanges establishes project version 1 in the authoritative publication transaction. When establishing trust from version 0, the compatibility duration catalog is pruned before the project marker advances: canonical workflow/template stages, existing official `ProjectStage` extensions and explicitly reviewed/submitted stage codes are retained, while duration-only legacy extension rows are removed because they may be abandoned private work. Retained legacy duration values are cleared to null before reviewed/current publication values are applied. Omitted legacy private values and stage codes cannot become trusted accidentally. Approval rollback includes the marker, compatibility rows, official dates, snapshot and approval metadata. New drafts, fallback reads and realignment consume only the accepted baseline, excluding other actors' proposals. Realignment keeps its approved-source date clone/shift algorithm and owner-null automatic submission, creating a complete version 1 proposal.

When accepted `Project.PncApplicable` is false, proposal initialization/upgrade and realignment set proposal PNC false, PNC duration zero and PNC planned dates null, even if retained official history or compatibility durations contain stale values. Initialization leaves official history intact. Explicit submitted positive Duration PNC or both submitted Exact PNC dates may enable the proposal. Approval follows the proposal flag and publishes null compatibility PNC duration when false. Known stages use canonical template/workflow order; extensions use accepted duration/official order and deterministic fallback.

Apply migration and matching application under the [offline update/rollback SOP](deployment/offline-ws2022.md#d-offline-update-and-rollback-sop). Quiesce planner writes across every old process/worker and resume only on the matching release: older writers bypass both markers, so additive columns do not support mixed-version planner writes. Preserve the SOP's compatible database/application backup or reviewed reverse-migration rollback path; never edit deployed migration history. No production configuration or production data has been inspected. Forecasting, approval-rule redesign and pending-lock removal remain excluded.


### `Models/ProjectComment.cs`
Supports threaded discussions around a project or a specific stage. Comments enforce minimum/maximum lengths, carry typed categorisation (Update, Risk, Blocker, Decision, Info), allow pinning and track soft deletion. Attachments and mentions are separate tables linked back to the owning comment with foreign keys and capture uploader metadata plus sanitised filenames for storage.

### Remarks (`Models/Remarks/Remark.cs`)
Structured project remarks capture author role, scope (general vs. ToT), typed body text, optional stage references, and event dates. Soft deletion preserves history while hiding entries. Each remark carries a concurrency token, audit trail (`RemarkAudit`) with immutable snapshots, and mentions that link to `ApplicationUser` records for @mention rendering. Role names normalise across admin vocabularies to keep analytics consistent. (see Models/Remarks/Remark.cs lines 1-160)

### Notifications (`Models/Notifications/*`)
* **`Notification`** – materialised rows that power the user-facing notification centre. Metadata columns (`Module`, `EventType`, `ScopeType`, `ScopeId`, `Route`, `Title`, `Summary`) come from the original dispatch envelope and timestamps track when a user sees or reads the item. (see Models/Notifications/Notification.cs lines 5-40)
* **`NotificationDispatch`** – queue table processed by `NotificationDispatcher`. It stores the serialised payload, retry counters, dispatch timestamps, and optional error text so failed deliveries can be diagnosed. (see Models/Notifications/NotificationDispatch.cs lines 5-44)
* **`UserNotificationPreference`** – per-kind opt-in/out switches evaluated before persisting new notifications. (see Models/Notifications/UserNotificationPreference.cs lines 3-10)
* **`UserProjectMute`** – association table that hides notifications for specific projects when the user has muted them through the API. (see Models/Notifications/UserProjectMute.cs lines 3-8)

### Project documents (`Models/ProjectDocument*.cs`)
* **`ProjectDocument`** – published artefacts with metadata (title, description, stage link, storage key, MIME type, file stamp, archival state) and a `RowVersion` concurrency token to prevent conflicting edits. (see Models/ProjectDocument.cs lines 13-78)
* **`ProjectDocumentRequest`** – workflow table that tracks document uploads/replacements/deletions before publication. Includes request type, reviewer metadata, temporary storage keys, and audit notes for approvals or rejections. (see Models/ProjectDocumentRequest.cs lines 23-85)

### Process templates (`Models/Stages/StageChecklistTemplate.cs`)
Stage templates drive the process designer UI and REST APIs:
* **`StageChecklistTemplate`** – versioned container per stage code with optimistic concurrency and audit trails. (see Models/Stages/StageChecklistTemplate.cs lines 8-29)
* **`StageChecklistItemTemplate`** – ordered checklist items with per-item row versions and editor metadata. (see Models/Stages/StageChecklistTemplate.cs lines 32-52)
* **`StageChecklistAudit`** – immutable log of checklist edits, including payload snapshots and timestamps for compliance reporting. (see Models/Stages/StageChecklistTemplate.cs lines 55-76)

### Intellectual property registry (`Infrastructure/Data/Ipr*.cs`)
`IprRecord` maintains filing metadata (number, title, notes, status lifecycle, filing/grant dates, optional project linkage) with a unique constraint on filing number + type and a row-version token for concurrency. `IprAttachment` stores uploaded evidence per record and references uploader/archiver identity for audit trails. Attachments are persisted under `ipr-attachments/{recordId}` via `IprAttachmentStorage`. (see Infrastructure/Data/IprRecord.cs lines 1-44) (see Infrastructure/Data/IprAttachment.cs lines 1-37)
