# Implementation Notes

## 1. Person-centric Find More Photos

`Find more photos` now projects two evidence sources into one review surface:

- direct unresolved-face → confirmed-person suggestions generated by the known-person matcher;
- current identity-group → confirmed-person suggestions generated from the grouping runtime snapshot.

Direct evidence is de-duplicated to one appearance per photograph. Group evidence is also reduced to one appearance per photograph and is removed when the same photograph already has stronger direct evidence for the target person.

The UI presents:

- **Strong possibilities**;
- **Moderate possibilities**;
- **Possible identity groups** with group-to-person similarity and group cohesion;
- lower-confidence direct possibilities in a collapsed section.

Nothing is preselected. Group-wide selection requires an explicit **Select all N** action. All mutations revalidate current evidence server-side before assignment/rejection.

### Scale boundary

“All possible” means all currently meaningful evidence for the selected person, not every unresolved face in the library.

- all currently relevant identity groups for the person are surfaced;
- direct candidate reads are bounded at 1,000 evidence rows for server safety;
- the review surface displays up to 120 ranked direct candidates in one profile load;
- lower-confidence direct candidates are collapsed rather than omitted from the loaded review set.

The current production workload is below that safety boundary. If the direct candidate population later grows beyond it, the next scaling step should be incremental `Show more` retrieval rather than rendering hundreds of additional face cards into the DOM at once.

## 2. PRISM User ↔ Media Person linkage

A new `MediaPersonUserLink` domain entity provides an explicit, human-governed relationship. The system never links users by name or biometric similarity automatically.

Active links are one-to-one through filtered unique indexes:

- one active PRISM user may map to at most one Media Person;
- one active Media Person may map to at most one PRISM user.

Unlinking is soft/history-preserving and requires a reason. Link/unlink events are recorded in Media Identity Audit.

Only active **Human** PRISM accounts may be linked. Hidden/merged media identities are not exposed as My Photos identities, but an existing active link remains visible to identity managers so it can still be corrected/unlinked.

## 3. Link-safe merge governance

Duplicate-person merge now treats the PRISM account link as institutional identity data:

- linked source + unlinked target → link transfers to the surviving target;
- source and target linked to different PRISM users → merge is blocked until a manager resolves one linkage.

## 4. My Photos and profile image integration

A linked user receives **My Photos** from the global user menu and a Photos Identity card on the account Profile page.

`/Photos?MyPhotos=true` resolves the current account to its linked Media Person and reuses the existing single-person Photos page. No second gallery implementation exists.

The existing Media Person representative portrait is reused as the navigation/profile avatar fallback. Image bytes are not copied into ASP.NET Identity. If the person representative is changed, consumers automatically resolve the new portrait.

## 5. Linked-user self review

When the signed-in account is linked to the person being viewed:

- `Find more photos` is personalised as **Find more photos of me**;
- candidate actions become **Yes, that's me** / **Not me**;
- the user may review only evidence for their own linked identity.

This does not grant identity-management privileges. Rename, merge, hide, trusted-reference governance and PRISM-user linkage remain under the existing identity-manager authorization boundary.

Self-confirmation remains `HumanConfirmed` and records `SelfConfirmed` as audit provenance. It never silently promotes an appearance to `TrustedReference`.

## 6. Rejection semantics

`Not me` / `Not <person>` is face-person specific. It does not:

- suppress the face;
- close the face as unidentified;
- reject other candidate people;
- automatically reject every member of an identity group.

A group-to-person suggestion is suppressed only after every current member of that group has been explicitly rejected for that person.

## 7. Processing-state behaviour

When no candidate is currently actionable but background matching is running, Find More Photos uses a compact processing state rather than a large empty review panel. Polling reports when new evidence is available but does not silently insert/reorder candidate cards while the reviewer is making selections.

## 9. Deferred intentionally

The optional unlinked-user **“This is me” claim → manager approval** workflow is not included in this phase. Explicit manager linkage is implemented first so the institutional one-to-one relationship is stable before adding a claim queue.
